Product Prototype Workspace for Real GitHub Repos

MVP này là một web workspace để product team demo feature mới trên chính codebase thật. Người dùng vào frontend và thấy repo đã được setup sẵn, có sandbox đồng bộ từ main, có nhiều prototype workspace riêng, và có thể chạy demo mà không chạm trực tiếp vào nhánh production.

Business Spec MVP Demo First Real GitHub Repo Sandbox Prototype

1. Một câu định vị

Đây là công cụ giúp team product và founder tạo, xem, so sánh và demo nhiều prototype feature trên một GitHub project thật, trong sandbox an toàn được sync từ main.

Mục tiêu của MVP không phải là code generation chung chung. Mục tiêu là làm cho buổi demo product có cảm giác thật: feature mới xuất hiện trong đúng app, đúng layout, đúng workspace, đúng context sản phẩm.

2. Product hoạt động như thế nào?

1. Main repo Repo GitHub thật của product, ví dụ app đang có module building và lease.
2. Sync Hệ thống đồng bộ codebase từ main qua workflow hoặc schedule.
3. Sandbox Bản nền an toàn để prototype, không làm bẩn main.
4. Checkout Tạo nhiều sandbox con như sandbox/abc hoặc sandbox/feature-a.
5. Demo Product xem feature mới chạy trong app thật, rồi quyết định giữ, sửa hoặc bỏ.

3. Business problem

Product muốn thấy feature thật trước khi build nghiêm túc

Mockup tĩnh không đủ. Product cần bấm được, nhìn được trong layout thật, và hiểu feature có hợp với app hiện tại không.

Engineering không muốn main bị nhiễu

Những ý tưởng chưa chắc chắn không nên đi thẳng vào production branch. Cần một nơi để thử nhanh, fail nhanh, và bỏ đi nếu không có giá trị.

Demo hiện tại thường thiếu context

Demo bằng Figma hoặc app giả khiến stakeholder phải tưởng tượng. MVP này demo ngay trên product thật nên quyết định business nhanh hơn.

Nhiều ý tưởng cần chạy song song

Một team có thể thử nhiều hướng như sandbox/abc, sandbox/xyz, sandbox/meeting-feature-4 mà không giẫm lên nhau.

5. Trạng thái khi user vào frontend

Trải nghiệm đầu tiên giống ảnh minh họa: user vào trang Prototypes, bên trái có workspace/project, giữa màn hình là prompt để yêu cầu setup hoặc chỉnh prototype, phía dưới là các prototype session đã tạo.

Repo đã được setup sẵn

  • Workspace biết repo GitHub nào đang được dùng.
  • User thấy tên repo, ví dụ social-media-web.
  • Không bắt user cấu hình technical ngay từ đầu trong demo.

Prototype sessions đã có

  • Mỗi session là một request hoặc feature prototype.
  • Card hiển thị số file thay đổi, diff summary và trạng thái.
  • User có thể mở lại session cũ để xem hoặc tiếp tục chỉnh.

7. Demo story cần thể hiện

  1. Người demo mở FE và chọn workspace đã gắn với GitHub repo thật.
  2. Trang hiển thị trạng thái repo: main đã sync sang sandbox, prototype sessions đang sẵn sàng.
  3. Người demo nhập prompt: "Add meeting feature for building lease workflow".
  4. Hệ thống tạo một prototype session mới, ví dụ sandbox/meeting-feature-4.
  5. Session hiển thị các thay đổi theo ngôn ngữ product: thêm layout, auth guard, workspace entry, current meeting view, component, service, hook.
  6. User mở preview và thấy feature chạy trong app thật, không phải mock UI rời rạc.
  7. Sau khi review, user chọn: tiếp tục chỉnh, discard, hoặc prepare handoff/PR cho engineering.

8. Các màn hình MVP

Màn hình User thấy gì? Mục đích demo
Workspace Home Repo hiện tại, trạng thái sync, nút setup agent, prompt box. Cho thấy product bắt đầu từ codebase thật.
Prototype Sessions Danh sách card: tên request, số file đổi, trạng thái ready/running/failed. Cho thấy nhiều prototype có thể chạy song song.
Session Detail Business summary, file diff summary, preview link, action tiếp theo. Giúp product review mà không cần đọc code sâu.
Preview App thật chạy trong sandbox branch/session. Moment quan trọng nhất: feature mới xuất hiện trong product thật.
Handoff Quyết định keep/discard/promote, notes cho engineering. Biến prototype thành quyết định business hoặc ticket kỹ thuật.

9. Prototype session gồm những gì?

Request

Prompt hoặc brief từ product, ví dụ "thêm meeting feature cho quy trình lease".

Sandbox branch

Nhánh hoặc workspace riêng để chứa thay đổi, ví dụ sandbox/meeting-feature-4.

Change summary

Tóm tắt bằng business language: thêm màn hình nào, flow nào, phần nào liên quan tới app hiện tại.

Preview state

Link hoặc trạng thái preview để user mở product thật và kiểm tra prototype.

10. Business value cần truyền tải

Faster product validation

Từ ý tưởng tới bản có thể bấm được trong app thật nhanh hơn cách viết spec rồi chờ dev.

Safer experimentation

Mọi thử nghiệm nằm trong sandbox, không ảnh hưởng main và không ép engineering merge sớm.

Clearer handoff

Khi prototype ổn, team có diff, preview, decision notes và context để chuyển sang build thật.

Moment Cần xảy ra trên màn hình Thông điệp business

12. MVP không làm gì ở bản đầu?

  • Không cần marketplace connector giống Alloy.
  • Không cần workflow automation tổng quát giữa nhiều third-party app.
  • Không cần phân tích toàn bộ codebase ở mức hoàn hảo.
  • Không cần merge tự động vào main.
  • Không cần giải quyết production deployment ngay.
  • Không cần UI builder kéo thả nếu prompt + session + preview đã đủ demo.

13. Câu hỏi business cần chốt trước technical

  • Repo demo chính sẽ là repo nào?
  • Feature demo đầu tiên là gì: meeting, dashboard, onboarding, hay workflow trong lease/building?
  • Preview cần mở app thật tới mức nào để stakeholder tin?
  • Session card cần hiển thị những chỉ số nào: file changed, diff, preview, status, owner?
  • Handoff cuối demo nên là PR, ticket, export spec, hay chỉ decision note?
  • Business persona ưu tiên là founder/product hay engineer?

14. Tóm tắt cách hiểu hiện tại

Product này là "prototype workspace trên repo thật". Nó dùng GitHub repo làm nguồn, tạo sandbox an toàn, cho phép checkout nhiều prototype branch, tạo feature theo request của product, preview trong app thật, rồi giúp team quyết định giữ, sửa, bỏ hoặc chuyển sang engineering.

Đây là bản business spec để thống nhất demo MVP. Chưa đi vào technical architecture, database, API hay queue.
